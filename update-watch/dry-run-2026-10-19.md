## 1. Run log

### Method and assumptions
- Tool: PubMed search tool (`search_articles`) with its date parameters set to `datetype=edat`, `date_from=2026/10/11`, `date_to=2026/10/19`, `max_results=60`. The tool turns these into `2026/10/11:2026/10/19[Date - Entry]` (seen in the returned query translation). I did not append `AND (... [EDAT])` to the query text; the effect is the same. The query strings below are the exact strings sent as `query`.
- Records read through `get_article_metadata` (PubMed record: title, abstract, DOI). Read level for every PubMed item below is **abstract** (PubMed record), never full text, unless stated.
- Assumption: where the plan says "read the whole result set", I read titles and abstracts for all hits of queries with fewer than 60 hits, except where stated in the table.

### Failures and errors
- 2 rate-limit errors (`RATE_LIMIT_EXCEEDED`, retryAfter 2) when 8 searches were sent in parallel: Q10 variant and Q12 variant a. Both were rerun successfully.
- 3 `get_article_metadata` calls and 1 `get_trial_details` call returned more than the tool's output limit (about 78,000 to 89,000 characters) and were saved to a file instead of shown. I read them with a short Python script (UTF-8 output had to be forced on Windows). No data lost, but 5 PMIDs requested in the Q5 batch were not returned (listed above).
- A PostToolUse hook error after writing this file: `tools/deliverable_reminder.py` was looked up in the folder above the project (the hook uses `$CLAUDE_PROJECT_DIR`, which resolved to the parent folder, not the project folder) and was not found. The file was written correctly. Unrelated to the watch queries, but it will show on every write in a session started from the parent folder.
- ClinicalTrials.gov tool (`get_trial_details`) does not return the last-update date. I filled that field from the public ClinicalTrials.gov API v2 with one `curl` call per NCT number (read-only; fields `OverallStatus`, `LastUpdatePostDate`, `EnrollmentCount`, `HasResults`). This is a departure from "use the ClinicalTrials.gov tool"; the status, enrolment and results flag from the tool and from the API agreed for all 7.

### Tool calls and cost
- About 50 tool calls in total (including 3 plan-file reads, 1 tool-loading call, 6 shell calls). Under the roughly 60 limit. I did not measure tokens; the three oversize metadata outputs were the largest items. I estimate well under the 150,000-token cap, but this is an estimate, not a count.
- Wall time was not measured.
- Time-consuming or unreliable steps: (1) metadata fetches for more than about 12 records overflow the output limit, so batches must be small or read from the saved file; (2) parallel search calls trigger rate limits; (3) the trial tool's output is very long (a single record exceeded 60,000 characters for NCT01101438); (4) Q5 and Q12 variant a are noisy.

### Plan and watchlist: unclear or not working
1. `randomized[pt]` in Q3 is not a valid publication-type term (use `"Randomized Controlled Trial"[pt]`), and even that returned zero for records new in the window; publication types are often added to PubMed records some days after entry. For RCTs use free-text words rather than `[pt]`.
2. `DRY-RUN-PLAN.md` says append `AND (... [EDAT])` to the query text. The PubMed tool has `date_from`, `date_to` and `datetype=edat` parameters, which do the same; the plan should name them.
3. "Read the whole result set when it is under about 60 records" was not workable for Q5 (62 hits) and Q12 variant a (61); both sit just above the threshold and are mostly noise. The plan should say what to do (rewrite the string) instead of screening the top 25.
4. The PubMed metadata tool returns a limited number of records per call (large batches overflow the output limit and 5 requested records were not returned). The plan should state a batch size of about 10.
5. Rate limits: sending more than about 6 PubMed searches in one parallel batch caused errors. State a batch size in the plan.
6. The ClinicalTrials.gov tool does not return the last-update date; the plan and `WATCHLIST.md` section 2 ask for it. Use the registry API (`https://clinicaltrials.gov/api/v2/studies/<NCT>?fields=...`) or add it to the check script.
7. `WATCHLIST.md` section 5 has no trigger for single C-peptide or insulin assay-standardisation papers (only JCTLM and EuBIVAS). Q5-Q7 will keep producing "minor" items unless a trigger or a rule to ignore them is written.
8. Mapping of "Affects" requires headings of the two deliverables; I was told to read only what I needed and did not read them. A claim ledger would remove this ambiguity (UPDATE-PLAN prerequisite 2).
9. NCT05760339 (PRINCESS) is listed as RECRUITING with a past completion date; a status check against the registry will not detect that the trial is probably finished. The watch should flag "completion date passed and status not updated".
10. `WATCHLIST.md` calls NCT06856291 (TRIM-IR) "observational"; the registry agrees. Its status is now COMPLETED (last update 2026-10-02), so a results posting or publication may come; no results were posted at baseline.
