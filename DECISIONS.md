# Decision log

Why the project is the way it is. Each entry: what was decided, why, what else was considered, who decided, and when to revisit. `CHANGELOG.md` records what changed; this file records the reasoning. Reconstructed on 2026-10-19 from the working conversation; add an entry whenever a decision is made, and read the relevant entry before changing a settled one.

Decided by: **user** = Jay; **joint** = proposed by the assistant and accepted; **assistant** = the assistant's default, open to change.

## Scope and method

**D-01. Question and scope.** Assess the clinical utility of measuring insulin resistance, and separately where insulin and C-peptide measurement is used. Coverage and reimbursement are out of scope for every role. *Why:* the user's focus; an early coverage role was dropped. *Decided by:* user (2026-10-18). *Revisit:* if a reimbursement analysis is wanted, run it as a separate project.

**D-02. The user sets role names and roles.** Roles were defined with the user's names and descriptions; early drafts were deleted. Final set: evidence searcher, endocrinologist, PCP, biostatistician, clinical chemist, scientist, skeptic, steelman, use-case reviewer, specialty reviewer, summary editor. *Decided by:* user.

**D-03. Evidence searcher and clinical chemist added after the first round.** Skeptic reviews showed retrieval depth (abstract-only reading, top-page screening) and assay variability/cutoffs were owned by nobody. *Decided by:* joint (2026-10-18).

**D-04. Scientist narrowed to on-call physiology.** Assay and cutoff questions moved to the chemist; clinical utility verdicts stay with the clinical roles. Its foundational claims must be sourced or tagged uncited. *Decided by:* joint.

**D-05. Independence and hub-and-spoke coordination.** Analysis-stage runs do not read each other's files; all coordination goes through the main session; peer messaging only for specific conflicts or handoffs, at most two messages each, anything received verified before use. *Why:* agreement between runs is meaningful only if they are independent; the chemist/searcher exchange helped modestly and showed messages crossing and a relayed error that only independent verification caught. *Alternatives:* free peer messaging (loses independence, correlated errors). *Decided by:* joint.

**D-06. Run mode: subagents by default.** The first round ran each role twice (separate sessions and subagents). Neither was clearly better; differences came from prompts, tools and instructions. The second run mostly measured how incomplete a single search is and cost 150,000 to 400,000 tokens per run. So: subagents for every role; sessions only when the user wants to watch or for peer messaging; never run the same role in both modes. The skeptic and steelman ran as sessions earlier only by the first pattern, not because they need to. *Decided by:* joint (2026-10-19). *Revisit:* if a controlled test (same brief, several runs in one mode) shows a real mode effect.

**D-07. Verification layers.** A skeptic checks every deliverable change before it is committed (local-files-only when the user's usage limit is tight); a steelman argues the opposite case; identifiers are checked against PubMed and Crossref; corrections get their own skeptic pass. *Why:* repeated findings of overstated grades, mislabelled studies, unverified negatives and copying errors in the merge. *Decided by:* joint.

**D-08. Confidence figures are judgements.** Bottom line 1 at about 80-85%, bottom line 2 at about 45-50%, stated as judgements of how likely the claim is to survive further checking, not computations. They were set before the measure-type rescoping and have not been re-derived. *Decided by:* assistant, reviewed by skeptics. *Revisit:* after the post-load and prediction gaps are searched.

**D-09. Use-case track.** A separate track lists uses of insulin and C-peptide by patient type (draft of 19, then 47 verified rows) through three area reviewers (hypoglycaemia/pancreas/transplant; classification/paediatrics; metabolic/liver/IR) and a consolidation step, then a skeptic. *Why:* the user wants to rank uses that could enter a clinical workflow. *Decided by:* user (2026-10-19).

**D-10. Specialty reviewer is analyst-side.** It checks the merged conclusion's IR claims from a specialty's view (cardiology first, also hepatology, reproductive medicine, nephrology, oncology, psychiatry), does not extend the use-case list, never stops to ask, and defaults to cardiology if no specialty is named; the main session names the specialty. *Why:* the user pointed out that use-case reviewers and analysts do different jobs. *Decided by:* joint.

**D-11. Summary editor is file-only.** It writes a plain-language summary from the project files with every sentence traced to its source and uncertainty labels kept; it runs after the specialty reviews. *Decided by:* joint. Not yet run.

**D-12. Conclusions are scoped by measure type.** The user asked whether fasting and postprandial insulin should be evaluated separately. A scope audit showed the bottom lines rest on fasting insulin/HOMA-IR and TyG/TG-HDL-C but were phrased as "IR measurement". Bottom lines were rescoped; post-load and C-peptide are evaluated only for niche uses; the two post-load prediction results in the files are nulls. Ten generic statements, relabelling use-case rows 17, 35 and 45, and a check of whether WBISI is the Matsuda index are deferred. *Decided by:* user raised it; joint.

**D-13. Paywalled papers are read at abstract level only.** Only open-access and repository full texts can be read. Detail claims rest on abstracts unless marked. A prioritised download list (about 20-30 load-bearing abstract-only papers) was offered and the user said not yet; PDFs must stay out of the public repository. *Decided by:* user. *Revisit:* when the user supplies PDFs.

**D-14. Usage limit awareness.** The user watches a usage limit. Search-heavy agent runs (specialty reviews, the scoring pilot, commonality searches) wait until the user agrees; file-only work is preferred meanwhile. *Decided by:* user.

## Use-case scoring

**D-22. Scoring rubric** (`usecases/scoring-rubric.md`). Dimensions scored 0-4: decision change, evidence for the decision impact, added value over alternatives (utility quality); guideline status, feasibility, workflow fit, safety (readiness); commonality (log bins, 0-5); stakes (0-4, the consequence of not having the information). Scored by dimension across all candidates by one agent each, not by use case. Calibration pilot on rows 6, 5 and 13, an agreement check on five candidates, deep dossiers for the top group, skeptic review of the ranking. *Decided by:* joint.

**D-23. Scoring parameters.** Commonality counted for the United States only (a patient = a patient in whom the clinical situation arises in a year: new cases plus those needing the test again; not tests, not everyone with the disease). Weights: utility quality 0.40, commonality 0.25, stakes 0.20, readiness 0.15, with a sensitivity check. Stakes is in the composite (the assistant's default was a separate label; the user preferred it as a scored dimension beside commonality). All candidates (about 30) are ranked and tagged by setting (routine care, specialist outpatient, inpatient or procedural). *Decided by:* user.

## Continuity and structure (added 2026-10-19)

**D-24. Project memory lives in the repository.** Memory notes (working style, file-location preference, lessons learned, pointer to the long working chat) are kept in `memory/` with an index in `memory/MEMORY.md`, and `CLAUDE.md` tells sessions to save new notes there instead of the private Claude memory folder (which holds only a pointer). *Why:* the built-in memory is private and tied to the folder name, so the rename orphaned it and it had to be recreated by hand; in-repo notes move with the project, are versioned and visible. The user has nothing personal to protect, so the folder is tracked and public. *Alternatives:* private memory only (not portable); a git-ignored in-repo folder (private but still path-independent). *Decided by:* user. *Revisit:* if anything sensitive needs remembering, keep that in the private folder. *Unverified:* whether new sessions follow the `CLAUDE.md` rule over the built-in memory behaviour; test in a new session.

**D-25. Folder split and script rename.** The old `update-system/` folder mixed four things and was split: `update-watch/` (update plan, watchlist, pending queue), `claims/` (claim ledger design and `claims.csv`), `tools/` (`check_citations.py`, the session-start script and its documentation in `tools/README.md`); `scope-audit.md` moved to `reviews/`. The session-start script was renamed from `session_brief.py` to `session_start_context.py` and now also prints the decision index and the memory index. *Why:* descriptive names and one purpose per folder. *Decided by:* user.

**D-26. Keep the tooling in this repository; no plugin or skill for now.** The hooks (`tools/session_start_context.py`, `log_session.py`, `deliverable_reminder.py`), `CLAUDE.md`, the decision log, handoff note and memory stay as repository files. *Why:* the user wants to keep the setup in one place and sees no need to reuse it elsewhere yet; two of the hooks are untested in live chats, so packaging them now would mean maintaining two copies. *Alternatives:* a plugin for the hooks and agents; skills for the end-of-session handoff and the skeptic-review step (both remain possible later). *Decided by:* user, 2026-10-19.

**D-27. Guard the public repository with permission rules and a pre-commit check.** `git push` asks each time, force pushes, hard resets and hook-skipping commits are denied, and a git pre-commit check (`tools/precommit_check.py`) blocks PDFs, `local_` session IDs, absolute paths and key-like strings. *Why:* the repository is public and a push cannot be undone; a session ID had already been committed once. *Alternatives:* a Claude hook on `git push` (cannot tell whether the user asked); relying on the rule in `CLAUDE.md` alone. *Decided by:* user (chose this improvement from the feature list), 2026-10-19.

**D-28. Update watch parameters.** Watch once a day during a tuning pilot of about two weeks (two-day PubMed window, tokens per run logged), then weekly; first-pass triage daily during the pilot too (user, 2026-10-19: the lean agent step costs about 27,000 tokens) and the user's own review of accumulated entries unscheduled (changed by the user from the proposed weekly watch with monthly triage); urgent items are reported only in `update-watch/PENDING.md` (the session-start brief shows the pending count); weekly PubMed screening starts at about 150,000 tokens and the retraction and registry checks should be scripts without a model where possible; scope is the IR conclusion and the use-case list; order of work is scheduling test, dry run, then scheduling. *Why:* the user watches a usage limit and wants the watch to be cheap and stay a reminder, not an automatic editor (D-18). *Alternatives:* monthly only; push notifications for urgent items; scheduling before a dry run. *Decided by:* user, 2026-10-19 (accepted the proposed defaults).

**D-29. Update watch: retrieval by script, judgement by model.** `tools/watch_fetch.py` does the PubMed queries, de-duplication against `update-watch/seen-pmids.txt`, trial registry checks against `update-watch/registry-baseline.json` and writes a compact candidates file; a model reads only that file. Papers of low relevance (single assay-standardisation papers, TyG studies without a PCE, SCORE2 or PREVENT comparator) are logged only, not entered in `PENDING.md` (`WATCHLIST.md` section 6). Watch state files are tracked in git. *Why:* the dry run cost 231,550 tokens against a cap of 150,000 because an agent searched and read everything; the scripted step reproduced the same hit counts and registry values in 13 seconds with no model. *Alternatives:* keep one agent for everything with a tighter cap (a cap cannot be enforced on an agent); scrap the watch. *Decided by:* user approved the proposal, 2026-10-19.

**D-30. Project goal: score the viability of use cases; clinical utility is the constraint.** The main goal of the project is to find the most viable uses of insulin, C-peptide and insulin-resistance measurement, and what would make the less viable ones viable, by scoring the use cases (rubric D-22 and D-23, plus a recorded path to viability). The assessment of whether routine insulin-resistance measurement is clinically useful (`merged-conclusion.md`) stays as the constraint behind it: it marks what not to pursue and gives research targets, and it is not repeated as a finding. D-01 keeps its scope (coverage and reimbursement out); this decision changes the emphasis. The one-page `summary.md` is rewritten as a viable-pathways brief and the long summary moved to `summary-detailed.md`. *Why:* the negative result on routine screening is known and accepted; the user wants guidance for targeting research and one job instead of two. *Alternatives:* keep two parallel goals; keep the long negative summary. *Decided by:* user, 2026-10-19.

**D-31. Update watch objective: viability signals.** The daily watch looks for signals that change the viability of a use case or reveal a new candidate use (S1 guideline, label or regulatory change; S2 a missing piece addressed; S3 assay or standardisation milestone; S4 new candidate use; S5 retraction or correction), each tied to the row or pathway it affects, and four queries (Q14 to Q17) track the closest-to-viable rows 48, 49, 9 and 5. It no longer exists to re-test the clinical-utility conclusion for its own sake. *Why:* after D-30 the two goals are one; the watch should feed the scoring and the research targets. *Alternatives:* leave the watch aimed at the old bottom lines; stop the watch until scoring is done. *Decided by:* user asked for a definite objective on 2026-10-19; the signal types are the assistant's proposal for the user to confirm.

**D-32. Scoring funnel.** Scoring runs as a funnel: stage 1 a cheap screen of all candidates by a lean agent (decision change, evidence, guideline status, patients per year, stakes, path to viability, tier), batches of at most 11 rows, with a search required for patients per year; stage 2 the full rubric (all roles, researched patient counts) on a shortlist of about 10 rows, run as one unit per role over the shortlist (about 6 units) so that scores stay comparable and the fixed cost per run is paid once; stage 3 per-row deep dossiers with all roles for the final 2 or 3 pathways, then a skeptic review of the ranking and the weights. Agents stop at 95% of the 5-hour window. The stage 1 screen is done for all 32 candidates. *Why:* ranking every candidate on every dimension would cost millions of tokens, and the goal (D-30) is to pick 2 or 3 pathways. *Alternatives:* all roles on every use case separately (about 150 runs); dimension scoring of every candidate by all roles. *Decided by:* user accepted the approach on 2026-10-19; the stage 2 and 3 split into per-role and per-row units was confirmed by the user on 2026-10-19 together with the stage 2 shortlist: rows 6, 5, 13, 31, 7, 3, 32, 47, 49, 4, 10 (rows 6, 5 and 13 are scored by the pilot units U1 to U6; the other eight by units V1 to V6).

**D-33. The watch feeds the scoring through proposals, never through edits.** The daily watch now (a) runs row-targeted queries (P-queries in `update-watch/queries.json`, one per row whose path to viability names a findable event, each tagged with the row) in addition to the topic queries; (b) writes a structured signals file (`update-watch/runs/<date>-signals.json`: type S1 to S5, rows, dimensions, PMID, DOI, note); (c) `tools/watch_to_queue.py` logs the signals in `update-watch/signals.tsv` and queues a rescore unit (R1, R2, ...) for S1, S2 and S3 signals that name rows. A rescore unit writes a proposal (`usecases/scoring/R<n>.json`, key `proposals`), which the aggregator does not read; a score changes only when the main session applies a proposal after review, keeping the original (`original_score`, `correction`). S4 new candidates and S5 integrity signals are only logged (S5 as urgent); queueing a screening unit for a new candidate is deferred until the first real S4 appears. The scorecard shows the latest signal per row and the session brief counts open signals. *Why:* the user asked how the watch could contribute to the use cases; the project rule is that scores and deliverables change only after review. *Alternatives:* let the watch rescore automatically (rejected: a single abstract rarely justifies a score change and the rule forbids it); keep the watch as text only. *Decided by:* user said ok to the proposal on 2026-10-20 (build points 1 and 2 and the logging of point 3).

**D-34. Article corpus in the repository, spreadsheet plus local full texts.** The project keeps a corpus of every article it cites (pilot: the PubMed IDs cited in `merged-conclusion.md` and `usecases-verified.md`, 143 on 2026-10-20) in `corpus/corpus.xlsx` (one row per article, automatic columns refreshed by `tools/corpus_build.py`, reading columns left for an extraction step and never overwritten), with a generated `corpus/corpus.csv` for version history. Full texts and PDFs live only in the git-ignored `corpus/fulltext/` folder, named by article ID (`C001.txt`, `C001.pdf`), as the user does for the separate eLFA corpus; the pre-commit check blocks that folder. The eLFA workbook (`I:/My Drive/SCIENCE/eLFA Articles.xlsx`, a device-technology corpus for a different project) is not merged: only a yes or no column by DOI says whether an article is also in it, and its column design (study type, key quantitative result, sample matrix, open access, citation confidence) was borrowed. *Why:* a corpus lets a score, a claim or a watch signal point to the papers it rests on, and lets a new session find what the project holds on a use case. *Alternatives:* one file per article; merging with the eLFA corpus; storing publisher texts in the repository (rejected: copyright, rule in CLAUDE.md). *Decided by:* user (scope: articles cited for any reason; format: spreadsheet; full text kept locally as PDF and text; build in this repository for now), 2026-10-20.

**D-35. Author contacts are collected locally, never in the repository.** To support letters of intent for the product work (a separate project from this evidence review), `tools/corpus_contacts.py` extracts the published corresponding-author contacts of the corpus articles (PubMed Central front matter and PubMed affiliations) into `corpus/local/`, which is git-ignored and blocked by the pre-commit check, because the repository is public and the data are personal.
